# Admin Command Centre, Taxonomy, and Responsive Operations Plan

**Date:** 2026-08-07  
**Branch:** `feat/admin-command-center-taxonomy-responsive-20260807`  
**Base:** `main` at `74cc5f7bd0aa0cc9b182c707079f45b74a939d00`  
**Status:** Implementation plan. This document is committed before application or database changes and is the release checklist for the work that follows.

## 1. Objective

Turn the Wewed parent-company Admin from a collection of individually useful screens into a coherent operational command centre that remains understandable as couples, planners, vendors, venues, client businesses, internal staff, and platform administrators grow in number.

The implementation must improve four things together:

1. **Taxonomy clarity:** external customers/partners, internal workers, and platform administrators must never be visually or structurally conflated.
2. **Responsive productivity:** the Admin must work as a dense, native-feeling interface on phones and tablets without requiring horizontal scrolling for primary workflows.
3. **Operational productivity:** Admin users need actionable queues, compact account summaries, and consistent account-level drill-down rather than manually scanning unrelated screens.
4. **Data-loop integrity:** new classifications and productivity records must reference canonical Wewed records, remain scoped by existing Admin permissions, and never create shadow copies of customer data.

## 2. Current architecture confirmed before this plan

The repository already has several foundations that this work must preserve rather than replace:

- `BusinessAccount.type` separates `couple`, `planning_company`, `venue`, `vendor`, `client`, and `wewed_internal` populations.
- `BusinessAccountMember` represents account membership separately from wedding membership.
- `PlatformAdministrator` and `PlatformAdministratorScope` provide a private Admin identity and scope layer.
- Client departments already model account-type-specific systems, data points, resource tools, and enabled department sets.
- Billing offers and billing profiles already separate pricing by account type.
- Admin account identity diagnostics already distinguish wedding memberships from account memberships.
- The existing Governance console includes separate Business Accounts, Platform Administrators, Permission Matrix, and Full Operations sections.

This release must build on those boundaries. It must not collapse them into a single generic `User` list.

## 3. Problems to solve

### 3.1 Human and account classifications are still too close together

The current account type correctly describes the business/customer population but does not answer:

- what subtype of vendor or planner the account is;
- whether a person is a customer, account owner, employee, contractor, or internal Wewed worker;
- which Wewed department owns an operational issue;
- whether a Wewed employee is also a platform administrator;
- which internal team should receive work generated by onboarding, billing, support, claims, or verification.

### 3.2 The Admin remains desktop-first on small screens

Observed and repository-confirmed issues:

- the Business Accounts table has a `min-width` around 1050px and therefore requires horizontal scrolling below desktop widths;
- the bottom Admin utility navigation itself is horizontally scrollable;
- large cards, headings, gaps, and padding consume too much vertical space on phone and tablet viewports;
- fixed bottom navigation and the fixed Account Identity control can compete for the same mobile safe area;
- primary Admin browser coverage does not currently exercise common Windows laptop widths such as 1280x720 and 1366x768.

### 3.3 There is no unified operational work queue

Approvals, onboarding problems, support cases, billing attention, provider claims, verification, and relationship mismatches exist in separate modules. Admin users have to discover work by visiting each area.

### 3.4 Account data is distributed across several useful screens

The data already exists, but the Admin needs one account-level drill-down that presents identity, people, lifecycle, enabled systems, billing, activity, risk, and audit history without widening the main registry.

## 4. Canonical taxonomy

The Admin will use a layered taxonomy. Each layer answers a distinct question and must not be overloaded.

### Layer A — population

- `external`: customer or partner organisation/person using Wewed services;
- `internal`: Wewed workforce or Wewed-owned system record.

Population is derived from canonical account/user relationships and is not a replacement for `BusinessAccount.type`.

### Layer B — account type

The existing `BusinessAccount.type` remains authoritative:

- `couple`
- `planning_company`
- `venue`
- `vendor`
- `client`
- `wewed_internal`

No existing account type is rewritten by this release.

### Layer C — account subtype

A controlled subtype describes the operating category inside an account type. Examples:

- vendor: photographer, videographer, caterer, florist, decor, entertainment, beauty, transport, stationery, rentals, cake, other;
- planning company: solo planner, planning studio, full-service agency, coordination-only, destination planner;
- venue: hotel, lodge, estate, garden, event hall, restaurant, destination venue, other;
- client: partner, corporate client, affiliate, supplier, other.

Subtypes are metadata for filtering and workflow routing. They do not grant permissions.

### Layer D — person relationship

A person's relationship to Wewed data is represented separately from account type:

- business owner;
- business member/employee;
- contractor;
- wedding member;
- customer/contact;
- internal staff member;
- platform administrator.

A person may have more than one relationship, but each relationship remains backed by its canonical record.

### Layer E — internal department

Internal Wewed workers may be assigned to a controlled department:

- Management
- Operations
- Marketplace
- Customer Support
- Billing & Finance
- Compliance
- Product & Engineering
- Sales & Partnerships

Department assignment is organisational metadata, not Admin authorization.

### Layer F — platform role and scope

The existing platform administrator role and scope model remains the security boundary. Being an internal worker does not automatically create platform access. Being a platform administrator does not automatically create an employment profile.

## 5. Database design and invariants

All database changes in this release must be **additive**. Existing customer, wedding, planner, provider, payment, membership, billing, support, and audit rows must not be rewritten or deleted.

### 5.1 `AccountSubtypeDefinition`

Private Admin schema table containing controlled subtype definitions:

- `subtypeKey`
- `accountType`
- `name`
- `description`
- `status`
- `sortOrder`
- timestamps

Unique constraint: `(subtypeKey, accountType)`.

### 5.2 `BusinessAccountClassification`

One classification record per business account:

- `businessAccountId` primary/foreign key;
- `accountType` mirrored and trigger-validated against `BusinessAccount.type`;
- nullable `subtypeKey`;
- optional `segment` for controlled operational segmentation;
- `assignedByUserId`;
- `version`;
- timestamps.

The row references the canonical BusinessAccount. It does not duplicate owner, billing, wedding, provider, or planner information.

### 5.3 `InternalDepartmentDefinition`

Private controlled department catalog:

- `departmentKey`
- `name`
- `description`
- `status`
- `sortOrder`
- timestamps.

### 5.4 `InternalStaffProfile`

Private workforce metadata linked one-to-one to the canonical `public."User"`:

- `userId` primary/foreign key;
- `departmentKey`;
- `jobTitle`;
- `employmentType` (`employee`, `contractor`, `advisor`);
- `employmentStatus` (`active`, `leave`, `suspended`, `left`);
- optional `managerUserId`;
- timestamps.

**Invariant:** no platform role or permission is derived from this table.

### 5.5 `AdminWorkItem`

Private operational queue item referencing canonical resources:

- `id`
- nullable `businessAccountId`
- `resourceType`
- `resourceId`
- `category`
- `priority`
- `status`
- `title`
- short `summary`
- nullable `assignedToUserId`
- nullable `departmentKey`
- `source`
- nullable `dueAt`
- nullable `resolvedAt`
- timestamps.

The table stores only operational metadata and references. It must not copy full support, claim, billing, wedding, guest, or provider payloads.

### 5.6 `AdminSavedView`

Private per-administrator preference table:

- `id`
- `administratorUserId`
- `name`
- `screen`
- `filters` JSONB object
- `sort` JSONB object
- `columns` JSONB array
- `isDefault`
- timestamps.

Saved views never alter query scope. Server-side Admin scope remains authoritative.

### 5.7 Security requirements

For every new table:

- schema remains private to server-side/Admin access;
- no direct `anon` or `authenticated` CRUD grants;
- foreign keys point to canonical records;
- JSON fields have shape checks;
- account-type mirrors are trigger-validated where used;
- updates that change classification/workflow ownership are audited through `BusinessAuditLog` or the existing Admin audit mechanism;
- migrations must be safe to run more than once where practical and must not drop existing data structures.

## 6. UI information architecture

### 6.1 Desktop

Keep a persistent left Admin navigation with compact sections:

- Command Centre
- Accounts
- People & Organisation
- Client Systems
- Commercial
- Onboarding
- Roles & Permissions
- Operations / Audit

The current Governance section remains the authorization owner for platform administrators and permission matrices.

### 6.2 Tablet

Use a compact icon/navigation rail or a two-row compact section switcher. Content cards use two or three columns where useful. Long record tables switch to compact record cards before horizontal scrolling becomes necessary.

### 6.3 Phone

Use a native-style bottom bar with no horizontal scrolling:

- Home
- Accounts
- Queue
- Alerts
- More

`More` opens a sheet/drawer containing secondary Admin destinations. The Account Identity tool moves into this navigation model instead of competing as an independent fixed bottom-right action.

## 7. Density system

### Phone target

- main headings: 22–26px;
- section headings: 18–22px;
- body text: 12–14px where readability allows;
- card padding: 10–12px;
- primary grid gap: 8–10px;
- category summary: 2 columns at 360–480px;
- touch targets remain at least 44px;
- no document-level horizontal overflow.

### Tablet target

- category summary: 3 columns where width permits;
- two or three compact record cards per row;
- sticky/rail navigation may be used where it does not reduce content width excessively.

### Desktop target

- retain dense tables for large registries where useful;
- account categories can display in one row;
- side navigation remains persistent.

## 8. Windows and horizontal scrolling remediation

Primary workflows must not rely on horizontal scrolling.

Implementation rules:

1. Business account table is desktop-only above the chosen breakpoint.
2. Below that breakpoint, accounts render as compact record cards with the same essential fields and actions.
3. Mobile Admin navigation does not use `overflow-x-auto` as the primary mechanism.
4. Any component that legitimately remains horizontally scrollable must provide visible overflow affordance, keyboard access, and stable scrollbar space.
5. Fixed controls must respect bottom safe-area spacing and must not overlap one another.
6. Browser tests include common Windows laptop viewports and explicitly assert that no essential action requires document-level horizontal scrolling.

## 9. Command Centre

The Admin landing view should show actionable metrics rather than forcing discovery through directories.

Initial cards:

- accounts pending review;
- onboarding blocked/incomplete;
- pending provider claims;
- pending provider verification;
- billing attention/past due;
- open high-priority support cases;
- planner relationship mismatches;
- invitations awaiting acceptance.

Below the metrics, show `My work queue` filtered by current administrator scope and assignment.

This first release may generate queue projections server-side from canonical tables and persist explicit work items only for manual assignment/triage. A later release may add database triggers or jobs for automatic work-item generation once event semantics are stable.

## 10. Account 360

Selecting an account opens a responsive drawer/page with these sections:

- Overview: identity, account type/subtype, lifecycle, owner, onboarding;
- People: owner, business members, invitations;
- Services: enabled departments, systems, resource tools;
- Commercial: billing offer/profile, payment attention;
- Activity: linked weddings/providers/planner relationships and recent operational activity;
- Governance: risk flags, classification, audit history.

The registry stays compact; detailed information moves into Account 360.

## 11. Commercial / pricing catalog

The existing account-type-specific BillingOffer model remains authoritative. The UI will expose it as a read-oriented pricing catalog grouped by account type, showing:

- offer name/code;
- billing model;
- monthly/annual or contract posture;
- included departments/entitlements;
- active/retired state;
- self-service eligibility.

Editing/versioning of offers is deliberately excluded from the first release unless the existing billing API already provides a safe audited mutation path. No destructive direct pricing edits will be introduced simply for UI completeness.

## 12. Delivery phases

### Phase 0 — plan and live database audit

- Commit this document first.
- Capture live table counts and critical fingerprints.
- Confirm existing BusinessAccount type distribution, Admin registry, client department/billing integrity, and current privileges.
- Verify proposed names do not collide with existing tables.

### Phase 1 — additive taxonomy and productivity schema

- Add subtype definitions and account classifications.
- Add internal department and staff profile tables.
- Add Admin work item and saved view tables.
- Seed only controlled definitions; do not infer or rewrite customer classifications unless a mapping is unambiguous.
- Add indexes and validation triggers.

### Phase 2 — Admin API

- Extend the existing governed Admin route or create a focused read route for command-centre/taxonomy data.
- Every account query remains server-scope filtered.
- Super Admin retains global visibility; restricted Admins receive only authorized account populations.
- Mutations require explicit permissions and audit reasons.

### Phase 3 — responsive shell and navigation

- Replace horizontally scrolling mobile Admin navigation with native-style bottom navigation + More sheet.
- Coordinate fixed safe areas and remove Account Identity control overlap.
- Add compact desktop/tablet/phone density classes.

### Phase 4 — registry and command centre

- Add Command Centre operational metrics and queue.
- Add 2-column phone / 3-column tablet category summaries.
- Replace account table with compact cards below desktop breakpoint.
- Add subtype and population filters.

### Phase 5 — Account 360 and organisation

- Add responsive account drill-down.
- Add People & Organisation read view for internal staff separate from platform administrators.
- Show administrator status only when the staff member also has a PlatformAdministrator record.

### Phase 6 — commercial catalog and saved views

- Add pricing catalog grouped by account type.
- Add basic saved-view persistence for account registry filters.

### Phase 7 — regression qualification

- lint and type/build gates;
- Admin governance contracts;
- migration chain and schema-diff gate;
- browser tests at 360x800, 390x844, 768x1024, 1024x768, 1280x720, 1366x768, and 1440x1000;
- explicit document-overflow checks;
- mobile navigation interaction tests;
- account-card parity with desktop table fields;
- authorization tests proving restricted Admins cannot traverse unscoped accounts;
- live database pre/post fingerprint comparison before any production migration.

## 13. Database non-regression gate

Before applying any production migration, capture:

- table counts for all current public and `wewed_admin` tables;
- row counts for critical customer/business tables;
- a stable aggregate fingerprint over canonical customer, account, membership, billing, provider, planner, payment, support, and audit records;
- current direct grants to `anon` and `authenticated` on private Admin tables.

After migration:

- all protected row counts and fingerprints must match exactly;
- only new tables/seed rows may differ;
- no existing account type, lifecycle, billing profile, membership, payment, wedding, provider, planner, support case, or audit record may change;
- new foreign keys/triggers must validate without orphaning existing data.

## 14. Definition of done

This release is complete only when:

- external accounts, Wewed workforce, and platform administrators are clearly separate concepts in both UI and data model;
- every account remains categorised by canonical account type and may optionally have a controlled subtype;
- Admin mobile navigation works without horizontal scrolling;
- the Business Accounts experience does not require horizontal scrolling below desktop widths;
- 2–3 row/column responsive density materially increases above-the-fold information on phones/tablets;
- Account Identity no longer collides with bottom navigation;
- Command Centre and Work Queue provide a useful first operational view;
- Account 360 centralises existing account data without copying it;
- internal workforce department metadata never grants Admin access;
- pricing remains account-type-specific and uses the existing segmented billing model;
- clean migration, build, browser, security, and database fingerprint gates are green;
- implementation report maps every delivered item back to this plan and explicitly lists deferred items.
